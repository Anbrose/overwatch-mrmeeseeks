# 赛事推送：改期去重与 preview 测试入口

日期：2026-10-18

这两项修复从「赛事竞猜」的设计（`esports-predictions` 分支上 `2026-10-18-esports-predictions-design.md` 的第 0 节）中拆出来，先行上线。它们不依赖竞猜。

## 1. 同一场比赛被重复提醒（线上 bug）

**现象**：2026-10-17，线上 `#esports` 频道。Liquipedia 把开赛时间推迟了 10–15 分钟，比赛 ID（`赛事路径|开始时间|队1|队2`）随之改变，同一场比赛收到了两条开赛提醒：
- Team Liquid vs The Kafe：21:15、21:40 各一条；
- NTMR vs Disguised：22:45、23:10 各一条。

**修复**：
- 比赛 ID 的格式**不变**，现有的 `esports_state.json` 可以原样沿用。
- 去重时增加一条容差规则：`reminded` / `resulted` 中如果已经有同一个 `赛事路径（含 #轮次）|队1|队2`（即 `match_base`），并且两者开始时间相差 **小于 6 小时**（`SAME_MATCH_WINDOW`），就视为同一场，不再发提醒或赛果。
- 改期后的新 ID 不再单独记账，每次都按容差规则识别。
- 旧记录的 ID 如果仍在当前比赛列表里，说明那是另一场比赛（比如季后赛同一页面里几小时后的重赛），不算改期：改期时旧 ID 会从 Liquipedia 消失，重赛时前一场还在列表上。
- 不是 `赛事|时间|队1|队2` 格式的 ID（例如测试里的 `"a"`）按原样比较。

**不受影响**：
- 同样两队相隔 6 小时以上再次交手；
- 同样两队在不同赛段交手（赛事路径不同，比如小组赛和季后赛）。

**已知限制**：同一赛段里同样两队在 6 小时内重赛，并且前一场已经不在 Liquipedia 汇总页上时（汇总页只保留最近约 50 场已结束的比赛），第二场的提醒和赛果会被吞掉。

## 2. `@mrmeeseeks esports preview`（测试入口）

**目的**：部署之后、或者新频道绑定赛区之后，测试人员可以马上验证推送效果和分流，不用等到下一场比赛或第二天 10:00。

**行为**：
- 立刻在当前频道发出一组样例，用的是**真实数据**，每条都以 `🧪 Preview` 开头：
  1. 未来 24 小时的预告；
  2. 下一场比赛的开赛提醒；
  3. 最近一场比赛的赛果（照常加剧透遮罩）。
- 提醒样例跳过双方都是 TBD 的比赛，和真实推送一致；预告样例在拆分时把前缀长度算进去，加上前缀后每条也不超过 1990 字符。
- 只包含会**路由到当前频道**的比赛（`EsportsFeed.channel_for(m) == 当前频道`）：当前频道绑定了哪些赛区，就是哪些赛区的比赛；如果当前频道是默认频道，就是没有绑定赛区的比赛。
- 没有可用的比赛时，回复 "No matches routed to this channel right now:"，并说明原因：数据还没抓到，或者没有比赛路由到这个频道（提示用 `esports status` 和 `region` 检查）。
- 不记账（不修改 `esports_state.json`），可以重复触发，不影响自动推送的去重。
- 需要"管理频道"权限。样例不 ping 任何人。

**实现**：
- 纯函数 `esports_feed.preview_posts(now, matches, routed_here) -> list[str]`；
- `EsportsFeed.preview(channel_id, now=None)`；
- `bot._esports` 新增 `preview` 分支，并在 `HELP_TEXT` 中加上说明。

## 测试

全部离线运行，在 Python 3.12 生产镜像里跑。

- **`tests/test_esports_feed.py`**：
  - `test_reschedule_dedupe`：用线上的真实例子。推迟 10 分钟后不再提醒，赛果也不重复；相隔 6 小时以上算另一场；不同赛段不受影响；旧格式的 ID 原样比较。
